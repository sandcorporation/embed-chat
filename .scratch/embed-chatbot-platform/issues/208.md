## What to build

TenantAgent에 역할(Tenant Admin / Tenant Member)을 도입하고, 인가를 **역할이 아니라 Permission 비트**로
검사하는 단일 모듈을 세운다. *되돌리기 어렵거나 라이브를 끊는* 조직 단위 3종만 Admin 전용으로 막고, 나머지
일상 운영(문서·HITL·Provider 키 포함 설정·전 조회)은 Member도 그대로 한다.

- 인가 deep module: Permission 카탈로그(`agents.manage`, `tenant_key.rotate`, `slug.change`)와 역할→비트
  프리셋(Admin=전체 / Member=전체−3종). `has_permission(subject, perm)`는 TenantAgent면 그 역할로,
  **Tenant(=TENANT_KEY 인증) 주체면 Admin 등가(전체 허용)**로 판정. 엔드포인트는 `require_permission(perm)`
  가드로 보호.
- 가드 적용: 팀원 생성/비활성화 = `agents.manage`, TENANT_KEY 회전 = `tenant_key.rotate`, Slug 변경 =
  `slug.change`. 팀원 생성은 `role`을 받되 기본 Member.
- 역할 노출: list_agents 응답과 어드민 Access Token에 역할을 실어, UI가 추가 왕복 없이 게이팅하게 한다.
- 마이그레이션: 기존 활성 TenantAgent 전원을 Admin으로 백필(현 접근·권한 보존). Operator가 생성하는
  Tenant의 첫 agent도 Admin.

## Acceptance criteria

- [ ] Member 자격증명으로 팀원 생성/비활성화·reset-key·Slug 변경 호출 시 403, Admin은 정상 동작
- [ ] TENANT_KEY 인증으로는 위 행위가 Admin 등가로 허용된다(break-glass·프로그램 프로비저닝 유지)
- [ ] 팀원 생성 시 role을 지정할 수 있고, 미지정이면 Member로 생성된다
- [ ] list_agents·Access Token에 역할이 포함된다
- [ ] 마이그레이션으로 기존 활성 TenantAgent가 Admin이 된다
- [ ] 인가 판정·게이트 엔드포인트 행위 테스트 그린(실 DB, 외부 경계 mock 없음)
