## What to build

110에서 facade(`api.ts`)로 CRUD를 생성 클라이언트로 전환했고, 컴포넌트는 시그니처 호환을 위해 `.jsx`로 유지했다. 이 슬라이스는 9개 컴포넌트 + 4개 페이지 + App/main을 **`.tsx`로 strict 전환**해, 생성된 타입(TenantConfigOut/AgentOut/EscalationOut 등)을 컴포넌트 레벨까지 적용한다.

탐색 결과 `.tsx` 전환 시 **약 247개 strict 타입 에러**가 발생한다(카테고리):
- useState가 API 데이터로 좁게 추론됨 → 생성 모델 제네릭 필요(`useState<AgentOut[]>([])`, `useState<TenantConfigOut|null>(null)` 등)
- 이벤트 핸들러/콜백 implicit-any(`e`, `id`, map 콜백) → 타입 부여
- 컴포넌트가 접근하는 모델 속성을 생성 타입으로 검증(실제 타입 안전의 핵심)
- 인라인 `style={{…}}` 리터럴의 CSSProperties 유니온 불일치 → 캐스트/정리 (styles.ts는 이미 any 타입화됨)
- `react-force-graph-2d` 타입 선언(필요 시 `declare module`)

## Acceptance criteria

- [ ] 9개 컴포넌트 + 페이지 + App/main이 `.tsx`로 전환되고 `tsc --noEmit` 통과(strict)
- [ ] API 데이터 상태/핸들러가 생성 모델 타입으로 타이핑됨(implicit-any 제거)
- [ ] ConfigTab.test가 `.tsx`로 전환되고 GREEN(`vi.mocked` 등 타입 정리)
- [ ] admin 전체 vitest GREEN(docker)
- [ ] **Playwright admin e2e로 회귀 검증**(operator/tenant-agent/hitl/visitors/graph) — 컴포넌트 동작 불변
- [ ] facade·mutator·생성 클라이언트는 무변경(이 슬라이스는 컴포넌트 레이어 한정)

## Comments

- 110에서 분리한 이유: facade 전환은 vitest+tsc로 즉시 검증 가능한 고가치 부분이라 먼저 확정.
  컴포넌트 strict 이관은 대량 cosmetic 수정 + 테스트 없는 9개 컴포넌트라 검증이 Playwright e2e(무거움)에 의존 → 별도 슬라이스로 안전하게 분리.

### 진행 결과 (구현 완료, e2e 검증만 미결)

- 9개 컴포넌트 + 페이지 + App/main + ConfigTab.test 전부 `.tsx`로 이관, **tsc --noEmit strict EXIT 0**(224→0), **vite build ✓**(1085 modules), admin **vitest 22 GREEN**.
- strict가 잡은 실제 갭 2건 처리: TenantOut.created_at 노출(생성일 컬럼 복구), KnowledgeGraph의 죽은 source_document_ids 제거.
- **Playwright admin e2e는 미검증(인프라 차단)**: e2e 백엔드 이미지(api-e2e/worker-e2e)가 **이번 auth 사가(issue 98~) 이전 상태**(마이그레이션 tenants.0005까지, RefreshToken 0012·신규 auth 엔드포인트 없음)라 stale이다. 새 admin이 구 백엔드와 통신하므로 e2e가 성립하지 않는다. 이는 112 이전부터 존재한 e2e 인프라 staleness이며, 컴포넌트 코드와 무관(admin-e2e는 빌드·healthy됨).
- **후속 필요**: `docker compose -f docker-compose.test.yml build api-e2e worker-e2e admin-e2e widget-e2e` 로 e2e 스택을 현재 코드로 재빌드한 뒤 `... run --rm e2e` 실행(전체 auth 사가 98~112를 e2e로 한 번에 검증). GPU 풀스택 + 브라우저라 무겁다.
