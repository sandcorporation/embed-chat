# Chat 전용 큐 + 전용 워커 격리 (prefork 튜닝)

## Parent

PRD: `.scratch/embed-chatbot-platform/PRD-chat-agent-celery.md`

## What to build

인터랙티브 chat이 무거운 배치(`ingest_document`, `rebuild_graph_communities` 등)에 인질로 잡히지 않도록, chat 태스크를 전용 큐·전용 워커로 격리한다. 이것이 PRD Q1에서 "브로커 홉을 감수한다"고 한 전제(큐 대기 ≈ 0)의 청구서다.

- **큐 라우팅.** `CELERY_TASK_ROUTES`로 `run_chat_agent_task`를 `chat` 큐로 보낸다. 배치 태스크는 기존 기본 큐 유지.
- **전용 워커 서비스.** docker-compose(dev/prod/base + test e2e)에 `worker-chat`을 추가해 `chat` 큐만 소비한다(`celery -A config.celery worker -Q chat`). 기존 `worker`는 배치 전담(필요 시 명시적으로 기본 큐만 소비하도록 정리). 단일 워커가 두 큐를 모두 청취하는 안은 격리가 안 되므로 채택하지 않는다.
- **prefork 튜닝.** chat 워커는 prefork(프로세스 격리가 이관의 본질, gevent는 블로킹-허브 재발). `worker_prefetch_multiplier=1`로 긴 태스크의 head-of-line 블로킹을 막는다. `task_soft_time_limit≈90s` + `task_time_limit≈120s`로 매달린 LLM이 프로세스를 영구 점유하지 못하게 한다(LLM 경계에 앱 타임아웃 없음). 시작 `--concurrency`는 보수적으로(예 4) 두고 처리량은 replica로 확장.
- **soft time limit 처리.** `SoftTimeLimitExceeded` 발생 시 `publish_error`로 사용자에게 알리고 정리한다(81의 예외 경로와 일관).

## Acceptance criteria

- [ ] `run_chat_agent_task`가 `chat` 큐로 라우팅된다(라우트 설정으로 확인)
- [ ] `worker-chat` 서비스가 compose에 존재하며 `chat` 큐만 소비한다
- [ ] 기존 `worker`는 chat 큐를 소비하지 않는다(배치가 chat 슬롯을 점유 불가)
- [ ] `worker_prefetch_multiplier=1`, `task_soft_time_limit`/`task_time_limit`가 설정된다
- [ ] soft time limit 초과 시 `publish_error`가 발행되고 태스크가 정리된다
- [ ] chat 워커는 prefork(non-gevent)로 기동된다
- [ ] 81의 기존 테스트가 EAGER 모드에서 라우팅 설정과 무관하게 계속 통과한다
- [ ] 테스트: 라우팅/타임리밋은 설정 단위로 검증, 실행 동작은 EAGER. 진짜 큐 격리(별도 워커)는 인프라 설정이므로 단위 테스트 대상이 아님
